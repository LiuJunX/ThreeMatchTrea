StandardMatchProcessor 重构 — 炸弹时序边界（修正版）

修正了上一版错误的场景，重新分析真实的行为差异

1. 上一版场景的错误

错误场景：(5,0) 放了一个 Square5x5 炸弹，同时声称它是 Group B 的 BombOrigin。

为什么错：MatchGroup.Positions 里的格子都是同色普通 tile（Item1~Item6）。 Square5x5 是炸弹类型，不参与颜色匹配，不可能出现在任何 MatchGroup 中，更不会成为 BombOrigin。

修正：BombOrigin 位置一定放的是普通颜色 tile（和 Group 的 Type 一致）。

因此：即使该位置被提前消除，消除的也只是一个普通 tile — 不会触发任何二次连锁爆炸。

上一版所说的「多了一整个 5x5 爆炸」不可能发生。

2. 真实的边界场景

那么两遍式和单遍式到底有没有区别？有，但只在跨 Group 共享位置 + 该位置是 BombOrigin 时出现，而且差异很小。

场景：L 形匹配拆成两个 Group，交叉点是 BombOrigin 且带 Cover

差异仅限于 BombOrigin 位置的 Cover/Ground 层是否多受一次伤害。 不会导致额外的连锁爆炸，不会改变消除的 tile 集合。

5. 这个场景会发生吗？

需要同时满足：

  • 两个 Group 共享一个 Position — 需要 L/T 形匹配被拆成两个 Group，或者级联中两个独立匹配恰好重叠
  • 共享位置恰好是某个 Group 的 BombOrigin
  • 该位置有 Cover 或 Ground（否则连这个小差异也不存在）

三个条件同时满足的概率极低，但非零。

结论：影响比第一版分析的小得多（没有额外爆炸），但两遍式仍然是更干净的方案 — 保持 Pass 1（所有 bomb spawn）不动，只把 Pass 2 改为逐 group 消除。成本几乎为零，彻底消除差异。

6. 推荐方案：两遍式（只改 Pass 2）

// Pass 1（不动）: 评分 + 所有 bomb spawn foreach (var g in groups) { points += score(g); if (g.SpawnBombType != None && g.BombOrigin.HasValue) { protectedTiles.Add(g.BombOrigin.Value); // ← 所有保护先建立 state.SetTile(..., new Tile(g.SpawnBombType)); } } // Pass 2（重构点）: 逐 group 消除 + 收集结果 foreach (var g in groups) { var groupEliminated = new List<(Position, Tile)>(); foreach (var pos in g.Positions) { if (globalCleared.Contains(pos)) continue; if (protectedTiles.Contains(pos)) continue; var result = Eliminate(pos); globalCleared.Add(pos); if (result.Outcome == Eliminated) groupEliminated.Add((pos, result.Tile)); } // TODO: obstacle adjacency notification // obstacleSystem.NotifyBatchElimination(groupEliminated, g.Type); }
